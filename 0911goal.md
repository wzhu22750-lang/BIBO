 ### 2. 最大风险是什么？                                                                   
                                                                                           
 不是简单的“用了 px”，而是文字、容器和可用视口分别按照不同规则变化。                       
                                                                                           
 当前主要机制是：                                                                          
                                                                                           
 - 大部分文字、图标、间距使用固定 CSS px；                                                 
 - WebView 可能额外放大文字；                                                              
 - fontScale.ts 尝试识别后，给部分文本反向 zoom；
 - 一部分容器按字体档位改变，一部分不变；
 - 页头、侧栏、导航、聊天又依靠独立的固定尺寸相互避让。

 这导致两种都需要防范的结果：

 1. **未检测到缩放：**文字变大，但对应布局保护没有启动。
 2. **检测到缩放：**部分保护启动，却扩大固定按钮、改变侧栏宽度、重复缩小子元素，制造新的比
    例或遮挡问题。

 ### 3. 当前最需要解决的五个问题

 1. 验证并明确系统字体缩放的检测与处理策略。
 2. 修复大字体样式与响应式布局之间的冲突，尤其侧栏与主内容错位。
 3. 取消聊天区域对固定页头/导航高度的假设，保证键盘和长关联消息下可操作。
 4. 让全屏提醒、更多菜单等浮层在短屏下能完整访问。
 5. 统一文字布局契约：长文本换行、固定按钮、图文比例、字体回退与重要文本可读性。

 ### 4. 已有的良好基础

 以下不应在整改时被误删：

 - index.html:7 已有 width=device-width、viewport-fit=cover、                              
   interactive-widget=resizes-content。                                                    
 - viewport 没有设置 user-scalable=no 或 maximum-scale=1。                                 
 - .button 主要使用 min-height，不是全面固定高度。                                         
 - 多处网格使用 minmax(0, 1fr)。                                                           
 - 聊天气泡已有 white-space: pre-wrap、overflow-wrap: anywhere。                           
 - 事件标题、回忆正文、邀请码、上传文件名等已有局部断行保护。                              
 - 通用 Modal 使用原生 dialog、max-height:88dvh、overflow:auto。                           
 - 项目并非“没有安全区实现”：Capacitor 8.5.1 内置 SystemBars 有 Insets 注入与键盘处理。    
 - capacitor.config.json 中 server.url 仍为规定的生产地址，未改变。

 ### B01. 字体缩放探针不能作为 WebView 文字缩放的可靠证明                                  
                                                                                           
 【严重程度】高，P0 基础项                                                                 
                                                                                           
 **【涉及页面/组件】**全站及全部大字体适配规则。                                           
                                                                                           
 【具体代码位置】                                                                          
                                                                                           
 - src/lib/fontScale.ts:35–75                                                              
 - src/lib/fontScale.test.ts:1–27                                                          
 - src/main.tsx:15–16                                                                      
 - src/styles.css:10–26                                                                    
                                                                                           
 【问题表现】                                                                              
                                                                                           
 探针测量的是：                                                                            
                                                                                           
 ```css                                                                                    
   height: 1em;                                                                            
   font-size: 100px;                                                                       
 ```                                                                                       
                                                                                           
 且元素没有文字内容。这测的是 CSS 元素布局高度，不是实际文字的字形高度或行盒大小。         
                                                                                           
 根字号 fallback 又依赖：                                                                  
                                                                                           
 ```ts                                                                                     
   getComputedStyle(document.documentElement).fontSize / 14                                
 ```                                                                                       
                                                                                           
 但根字号本身明确写成了 14px。                                                             
                                                                                           
 **【触发条件】**WebView 放大实际文本，而没有按同样系数改变空元素 em 几何尺寸或对外暴露的  
 computed font-size。                                                                      
                                                                                           
 【为什么不同手机/系统设置会产生差异】                                                     
                                                                                           
 系统字体比例、WebView text zoom、浏览器文本自动调整、页面整体缩放并不是同一机制；不同     
 WebView 版本和宿主设置不能保证都反映到该探针。                                            
                                                                                           
 【潜在影响】                                                                              
                                                                                           
 真实文字已放大，探针仍可能返回 1，导致 data-fs-grow/big/xl/xxl 不出现。整个分档保护因此没 
 有生效。                                                                                  
                                                                                           
 现有测试只验证数值截断与阈值分类，没有验证实际探针、Android 字体设置或浏览器排版。        
                                                                                           
 【建议解决方向】                                                                          
                                                                                           
 - 首先在真机对照系统 fontScale、WebView textZoom、探针结果、实际文本行盒。                
 - Android 宿主可提供真实配置作为诊断依据，但不要把系统 fontScale 直接等同于每段网页文字的 
   实际比例。                                                                              
 - 网页布局应在探针不可用时仍可重排，不能依靠探针才具备基本稳定性。                        
 - 不建议在未验证前继续扩大这套反缩放规则的覆盖面。

 ### B02. 大字体侧栏变宽，但主内容没有同步避让                                             
                                                                                           
 【严重程度】高，P0                                                                        
                                                                                           
 **【涉及页面/组件】**所有显示侧栏的页面，尤其手机横屏、平板。

 【具体代码位置】

 - src/fontscale.css:203–208
 - src/styles.css:203–215、383–385
 - src/styles.css:4389 起的 1250px 断点

 【问题表现】

 大字体规则无宽度限制：

 ```css
   html[data-fs-big] .sidebar {
     width: 250px;
   }
 ```

 但 .main-wrap 的左外边距仍按普通断点取值：

 │ 屏幕宽度    │ 主内容左外边距 │ 大字体侧栏宽度 │ 不一致 │
 ├─────────────┼────────────────┼────────────────┼────────┤                                
 │ 761–1020px  │ 84px           │ 250px          │ 166px  │                                
 ├─────────────┼────────────────┼────────────────┼────────┤                                
 │ 1021–1250px │ 190px          │ 250px          │ 60px   │                                
 ├─────────────┼────────────────┼────────────────┼────────┤                                
 │ >1250px     │ 220px          │ 250px          │ 30px   │                                
 └─────────────┴────────────────┴────────────────┴────────┘                                
                                                                                           
 **【触发条件】**视口大于 760px，且命中 data-fs-big。                                      
                                                                                           
 **【为什么不同手机/系统设置会产生差异】**横屏、折叠屏、显示大小调整会改变 CSS 视口宽度；  
 字体档位又独立改变侧栏。                                                                  
                                                                                           
 **【潜在影响】**固定侧栏遮住主内容左侧，包括表单、按钮、聊天内容；这是 CSS 层面可以明确确 
 认的尺寸冲突。                                                                            
                                                                                           
 **【建议解决方向】**侧栏宽度与主内容偏移采用同一布局源；避免固定侧栏宽度和独立            
 margin-left 各自维护。

 【严重程度】高，P1                                                                        
                                                                                           
 **【涉及页面/组件】**品牌、导航、每日任务、衣橱、里程碑、状态标签。

 - src/components/Shell.tsx:40–45

 【问题表现】                                                                              
                                                                                           
 .brand-word 和它的 span、i 都被设置 zoom:var(--fs-inv)。父子元素的几何缩放会叠加，感叹号  
 和装饰不再与品牌主体保持同样比例。

 【潜在影响】                                                                              
                                                                                           
 - 文本即使“恢复原大小”，旁边的 SVG 仍可能变小。                                           
 - 小字号重要信息不再跟随用户放大。                                                        
 - 像素描边、图标大小和视觉层级失去一致性。                                                
 - 品牌子元素额外缩小。                                                                    
                                                                                           
 **【建议解决方向】**区分装饰、品牌、数字和内容文本，避免以 .micro 作为统一反缩放入口；每  
 条祖先链只能有明确的一层尺寸策略。

 - src/styles.css:820–873

 【问题表现】

 ### B05. 聊天视口依赖固定高度预算，特殊状态可挤掉输入区域                                 
                                                                                           
 【严重程度】高，P0                                                                        
                                                                                           
 **【涉及页面/组件】**悄悄话、关联消息、离线快照、同步错误、键盘和快捷短语。               
                                                                                           
 【具体代码位置】                                                                          
                                                                                           
 - src/styles.css:1644–1664                                                                
 - src/styles.css:5161–5187                                                                
 - src/expectations.css:1207–1215                                                          
 - src/pages/Chat.tsx:177–186、279–355                                                     
 - src/components/LinkedRecordPanel.tsx:44–90                                              
 - src/App.tsx 中 Shell 内的缓存、错误、等待横幅                                           
                                                                                           
 【问题表现】                                                                              
                                                                                           
 移动端聊天使用：                                                                          
                                                                                           
 ```css                                                                                    
   height: calc(100dvh - 60px - var(--app-top) - var(--app-nav));                          
   overflow: hidden;                                                                       
 ```                                                                                       
                                                                                           
 桌面则使用 100vh - 71px。                                                                 
                                                                                           
 但是：                                                                                    
                                                                                           
 - 顶栏只有 min-height，不是永远等于 60/71px。

 - 关联消息面板位于聊天窗口之外，但仍在同一个固定高容器中。                                
 - 快捷短语区可多行增长。

 线/错误提示。

 **【为什么不同手机/系统设置会产生差异】**输入法高度、候选栏、导航模式、浏览器地址栏和
 WebView 键盘处理会改变实际可用空间。

 **【潜在影响】**消息列表被压到接近零高度；关联内容或输入区超出父容器后被裁切；发送操作难
 以访问。

 【建议解决方向】

 - 由应用容器按真实布局分配剩余高度，而不是扣固定常量。
 - 长关联记录需要明确的滚动归属。
 - 快捷短语区应有独立可用高度上限。
 - 为极短可视区域准备降级策略，必要时隐藏非必要导航，而不是继续叠加高度预算。

 ### 4. 尚未发生但值得提前处理的问题                                                       
                                                                                           
 ① 恢复长聊天草稿后，输入框高度可能不匹配内容。                                            
                                                                                           
 src/pages/Chat.tsx:329–342 只在 onChange 时重算高度，并硬编码最大 120px。恢复已有草稿、插 
 入快捷短语、字体变化、宽度改变不会走同样的重算流程。                                      
                                                                                           
 这也意味着 fontscale.css 放宽到 160/220px，不一定改变 JS 设置的实际高度。                 
                                                                                           
 ② 根节点横向裁切可能掩盖问题。                                                            
                                                                                           
 src/fontscale.css:259–260 的 overflow-x:clip 不能修复内容超宽，只会让用户不能滚动到超出的 
 内容。验收不能只检查页面有没有横向滚动条。                                                
                                                                                           
 ③ 旧 Bottom Sheet 重新启用会引入另一套尺寸预算。                                          
                                                                                           
 WardrobeDrawerLayout 当前没有进入正式衣橱入口，不算当前正式页面故障。                     
                                                                                           
 但 src/styles.css:2848–2851、3081–3087、3139–3164 保留了：                                
                                                                                           
 - 52/82vh；                                                                               
 - 半屏最小高度 320px；                                                                    
 - 桌面固定左偏移 220px。                                                                  
                                                                                           
 若未来恢复，会与现有 84/190/250px 侧栏及键盘场景冲突。                                    
                                                                                           
 ④ 用户 emoji 与程序装饰 emoji 应分开。                                                    
                                                                                           
 用户消息包含 emoji 应作为合法长文本测试。                                                 
                                                                                           
 但当前任务组件自身还有 emoji 庆祝图形，例如 DailyTaskCard.tsx 的完成横幅与粒子。它们会随  
 系统 emoji 字体改变颜色、尺寸、基线，也不符合项目要求的统一 SVG 图标路线。                
                                                                                           
 ⑤ 不同 DPR 下“像素感”不能保证物理像素完全一致。                                           
                                                                                           
 项目使用了 1.5px/2.5px 边框与投影、旋转、小数比例、字体 zoom。即使 SVG 是 crispEdges，在  
 不同 DPR 和 transform 下，仍可能出现硬边缘粗细与栅格对齐差异。                            
                                                                                           
 这主要是 P2 视觉问题，不应通过为品牌或 DPR 分别硬编码布局解决。                           
                                                                                           
 ⑥ 当前 QA 不足以证明跨设备稳定。                                                          
                                                                                           
 scripts/qa/shoot.mjs 主要按 430×930、DPR 2 拍摄部分页面；没有系统文字缩放、短屏键盘、全页 
 面状态的自动判定。                                                                        
                                                                                           
 现有字体测试不覆盖真实文字缩放。没有运行这些脚本，因为它们会生成文件，本次禁止写入。

 ### 5. 验收不仅看“是否溢出”                                                               
                                                                                           
 建议统一以下标准：                                                                        
                                                                                           
 1. 保存、发送、关闭、返回入口全部可见或可滚动访问。                                       
 2. 五个 Tab 布局区域等宽；图标和标签没有侵入相邻区域。                                    
 3. 重要文字不因容器裁切而丢失；省略文本有完整查看路径。                                   
 4. 标题与正文层级明确，不在档位变化时突然互换视觉权重。                                   
 5. 图标不因文字反缩放而额外缩小。                                                         
 6. 系统栏、键盘不遮挡关键操作。                                                           
 7. 空状态、错误状态、长内容状态均通过。                                                   
 8. 字体失败后允许合理重排，但不允许遮挡或无法操作。                                       
 9. 检查子元素边界和操作可达性，不能只以“无横向滚动条”判定通过。

# Goal：系统性修复 BIBU！跨设备 UI 稳定性问题

请根据上一轮《BIBU！跨设备 UI 稳定性诊断报告》，对当前项目进行系统性整改。

核心目标：

让 BIBU！在不同 Android 手机、不同屏幕尺寸、不同 DPR、不同系统字体大小、不同显示大小、不同导航方式、不同 WebView 环境下，都能够保持稳定、协调、可操作。

重点不是“让所有设备长得一模一样”，而是：

在保持 BIBU！现有像素风视觉体系、颜色、字体风格、卡片结构、图标、间距节奏和产品气质的前提下，让布局能够根据实际可用空间合理重排，而不是出现挤压、重叠、裁切、遮挡或无法操作。

⚠️ 重要原则：

1. 不要为了适配设备而大幅改变现有 UI 设计。
2. 不要把 BIBU！改成普通的 Material / iOS 风格。
3. 不要简单地把所有 px 改成 rem。
4. 不要通过大量设备型号判断来写 hack。
5. 不要针对 OPPO、vivo、小米等品牌分别写特殊 CSS。
6. 不要通过 overflow:hidden / clip 掩盖真正的溢出问题。
7. 不要继续无休止增加 font-size 档位来打补丁。
8. 不要删除现有已经稳定的视觉效果。
9. 优先建立统一的布局规则，再解决具体组件。
10. 每次修改后都检查是否破坏默认 390px 左右手机上的现有视觉效果。
